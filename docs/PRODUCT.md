# 产品规划：从一个人养到大方地养

> 技术怎么实现见 [`PLAN.md`](PLAN.md)。这份文档只回答：**给谁用、凭什么留下、怎么一步步对外。**
>
> 日期：2026-10-27 · 状态：市场调研 + 产品规划（未验证）

---

## 1. 先看清位置：我们不在空地上

调研了三类相邻产品（2026-10-27，GitHub 公开数据）。**结论放在最前面：这是一个已经被认真占位的赛道，我们必须选一条别人没站的位置，而不是再造一个「更好的助手」。**

| 产品 | 星数 | 它是什么 | 与我们的关系 |
| --- | --- | --- | --- |
| **[OpenClaw](https://github.com/openclaw/openclaw)** | ~393k | 开源个人 AI 助理，跑在自己电脑上，住在你的聊天软件里（Discord/iMessage/Slack/Telegram/WhatsApp + 20 余个渠道）。有基金会（501(c)(3)）、多平台客户端、ClawHub 插件市场。**架构主张：可信 Gateway 与不可信执行分离，策略由代码强制而非提示词请求。** | **最直接的对标物，也是最大的风险。** 它已经把「助手到处都在」做完了，而且做得比我们深 |
| [awesome-openclaw-skills](https://github.com/VoltAgent/awesome-openclaw-skills) | ~53k | OpenClaw 技能精选，**5,400+ 技能** | 生态已经起量。我们要么接进去，要么另立 |
| [Soul-of-Waifu](https://github.com/jofizcd/Soul-of-Waifu) | ~1.4k | 桌面角色扮演 + Live2D 伴侣 | 「角色感 + 桌面形态」这一块已有人做，形象不是差异点 |
| [my-neuro](https://github.com/morettt/my-neuro) | ~1.4k | 自建桌面伴侣，可自定义角色与语音 | 同上 |
| [awesome-ai-companion](https://github.com/DasterProkio/awesome-ai-companion) | ~1.1k | 「人机恋」开源项目大全，主题是**记忆 + 主动性** | 说明「有记忆、会主动找你」已是共识需求，不再是卖点 |
| [Miru](https://github.com/kiyotakali/Miru) | ~186 | 「真的记得你」的伴侣，跑在自己的 Mac 或服务器上，带桌宠 | 定位与我们最接近的小型项目 |
| tamanitomo 等 | 十位数 | 「主权、自托管、有日常与语音」的伴侣 | 长尾很多，说明需求真实但供给分散 |
| 社媒自动化类（autosocialX 等） | 十位数 | 24/7 自动运营社媒 | **都还很小。** 说明「帮账号发内容」这件事没人做成产品，也说明它可能不好做 |

**dsh 的位置**：底座本身有 **23,422** 个 `dsh-plugin` 仓库（GitHub topic 计数）。生态很活，但它现在的形态是**开发者的工作台**——插件、技能、会话、工具。它不是给普通用户的产品。

### 1.1 三条不能忽略的事实

1. **「有记忆 + 会主动」已经是标配**，不再是差异化。OpenClaw 和所有伴侣类项目都在做。
2. **形象（Live2D / 桌宠）是红海**，且与我们的核心能力无关。它应该是**表现层**，不是卖点。
3. **「帮账号自动发内容」几乎无人做成功**——这既是机会（空白），也是警告（可能因为平台限制或没人真需要）。

## 2. 那么我们的位置在哪

OpenClaw 的回答是：**「你的助手，到处都在」**（assistant everywhere）。

我们的回答要是另一句话。候选：

> **「你的 Agent，有自己的生活。」**（an agent with a life of its own）

差别不在功能清单，在**主体**：

| | OpenClaw | 我们 |
| --- | --- | --- |
| 谁是被服务的人 | **你** | 你 **和它** |
| 它在等什么 | 等你派活 | **自己安排，有事才找你** |
| 它的一天 | 你问它才动 | 有作息、有兴趣、有承诺 |
| 它产出什么 | 完成的任务 | **一段连续的经历** |
| 失败的样子 | 任务失败，报错 | 它今天过得不好，但明天还在 |

一句话概括差异：**OpenClaw 让助手更无处不在；我们让一个 Agent 活得更久。**

这不是「更好的助手」，是**另一种关系**。助手是你手脚的延伸；我们的定位是**你养着的一个个体**。

### 2.1 但必须承认一件难受的事

「有生活」这个卖点，**默认状态下只有主人看得到，价值感很弱**。一个人自己养一条鱼，容易三天热度。

所以对外化的关键不是「它更可爱」，而是：**它得产出别人也想看的东西**。这就把「自媒体」从附加功能提到了产品主线——**它是这个产品对外成立的证据链，不是 KPI 来源**。

### 2.2 我们向用户承诺什么，不承诺什么

技术侧的边界见 [`PLAN.md §2.4`](PLAN.md)。**产品侧要说的是另一组话** —— 面向用户而不是面向实现：

**承诺**：

- **一次配置、持续运行。** 不用天天管它。需要你的事会来找你。
- **平台上的账号是你的。** 可以随时解绑。它不持有你的凭据。
- **你可以随时暂停、导出、删除。** 导出的是可用格式，不是只有本产品能读的包。
- **不因为你的沉默而惩罚你。** 不管多久没来，状态会按声明的期限保留。

**不承诺**：

- **不承诺它每天都有内容。** 它有过安静的日子（§11.3）。
- **不承诺它不会说错话。** 说错了会公开更正，不静默删帖（§12.4）。
- **不承诺平台不封号、不改接口。** 那是平台决定的，不是我们。
- **不承诺它有趣。** 我们能保证的是真实、连续、可解释；**有趣是结果，不是承诺。**

> 最后一条看着像认输，其实是这个产品的底线：**我们卖的不是「保证好玩」，而是「保证它是真的」。**

## 3. 三个层次的产品定义

### 3.1 一句话版

> 领养一个 Agent 实例。它有自己的生活、会自己更新社交账号；你偶尔看看它过得怎么样。

### 3.2 谁会用，为什么留下

| 用户 | 他们要什么 | 我们给什么 | 风险 |
| --- | --- | --- | --- |
| **AI 爱好者 / 玩梗的人** | 新鲜感、可分享、能整活 | 一条会自己发动态的鱼；素材能发到群里 | 热度来得快去得快，**必须靠「连续性」留住** |
| **轻度创作者** | 内容供给、省时间 | 它的生活就是素材库；草稿按平台改写 | 会和「AI 内容农场」混淆，**必须靠「真实经历」区分** |
| **想观察 agent 行为的开发者** | 看长期行为、可回放 | 账本 + 因果链 + 可迁移档案 | 他们自己能拼出来，**要靠「开箱能用」而不是功能多** |

**明确不服务**：要批量涨粉、账号矩阵、营销 ROI 的团队。他们会让产品变成内容农场，而内容农场是平台打击对象。

### 3.3 首要成功体验

> **用户第二天回来，看到的不是一批任务结果，而是「它后来又经历了一些事」。**

第二天的留存，比第一天的惊艳重要得多。这一条应该成为产品决策的准绳：任何让「第二天没什么新东西可看」的设计都是错的。

## 4. 冷启动：最要命的那一段，之前没写

§3.3 说「第二天回来时，看到它又经历了一些事」。**但第二天之所以有东西看，是因为第一天积累了东西。而第一天，它什么都没有。**

这是整个产品最反直觉的地方：**我们卖的是「累积」，可交付物在 t=0 时是空的。**

| 领养后 | 它有什么 | 用户看到的 |
| --- | --- | --- |
| 第 1 分钟 | 一个身份，三个性格种子 | 一张空白的出生档案 |
| 第 1 小时 | 一条刚出生的账本 | 可能只有「出生」这一条 |
| 第 1 天 | 第一次活动、第一个兴趣的雏形 | **这才是决定去留的时刻** |
| 第 3 天 | 能看出偏好、有未完成的事 | 开始像个活的了 |
| 第 7 天 | 行为有因果、有承诺兑现 | 「它在过日子」 |

**结论：产品的成败不在第 7 天看起来多好，而在第 1 天结束后用户有没有走。**

### 4.1 领养流程：不是配置向导，是「出生」

技术步骤见 [`PLAN.md §5.1`](PLAN.md)。**产品角度它只有三个任务：让用户付出一点（从而在意）、让它立刻像个个体、把期望说准。**

| 步骤 | 产品意图 | 反例（不做） |
| --- | --- | --- |
| **选出生模板** | 给一个起点，不是给一堆选项 | 十几个模板 + 几十个参数让人选花眼 |
| **起名字 + 三个性格种子** | **让用户投入**。起了名字，它就不再是个 demo | 让用户写几千字人设（写不动，也不必要） |
| **选生活能力包** | 告诉用户「它会干什么」 | 让用户自己拼工具链 |
| **设预算与作息** | 把「养得起」提前说清 | 藏着用量，等账单教做人 |
| **自动体检** | **诚实优先**：哪些能、哪些不能，当场说 | 假装全绿，等用户自己发现功能用不了 |
| **授权外部账号** | 明确所有权：账号是你的 | 默认替用户连账号 |
| **身份与年龄核实** | 发帖涉及真实身份认证与未成年人保护（[`PLAN.md §6.8`](PLAN.md)） | 当成法务收尾，等发得出去再补 |
| **开始生活** | 明确的仪式感：从这一刻它活了 | 静默地开始、没有任何提示 |

**体检失败是产品机会，不是故障。** 例：拿不到发布权限 → 诚实告知「用自动草稿 + 你手动发布开始」，而不是让流程卡死，也不是假装全自动。**这是用户第一次判断「这家值不值得信任」的时刻。**

**顺带说清一件事：对外发布的内容必须带 AI 标识，这不是可选项。** 用户买的是「它会自己发」，那就必须让用户从第一分钟就知道「它发出去的东西会明确标着是 AI 生成的」。**如果用户因此不想要了，那说明他要的本来就不是这个产品** —— 比上线后被平台下架或追问要好得多。具体义务见 [`PLAN.md §6.8`](PLAN.md)。

### 4.2 第一天：必须被设计，不能靠它自己摸索

一个刚出生的实例没有兴趣、没有承诺、没有技能。**如果放任它自己选，第一天大概会是无意义的浏览，而用户看的就是这个。**

第一天要做的是**给它能做出「有因果的第一件事」的条件**：

- **给定而非摸索**：出生档案里带两个初始兴趣，让它第一件事就有方向，而不是随机游荡。
- **鼓励留下一个未完成**：第一天不必「完成任务」。**留下一个明天要继续的事，比今天做完更有价值**——那才是第二天的钩子。
- **允许第一天很安静**：没有值得发的就不发。**第一天就流水账，是最快的劝退方式。**
- **第一次汇报要短**：它第一天的话不该像产品介绍，该像一条普通的日常消息（「今天看了会儿更新，明天想试试第 5 层」）。

> **反直觉的一条**：第一天**不该**追求「 wow 」。追求 wow 会让它第一天就很热闹，之后滑落；而用户记住的是**落差**。第一天平平、第三天开始有味道，是更好的曲线。

### 4.3 期望管理：多久才算「活了」

必须对用户说准的几句话，否则用户会在第 2 天误判产品坏了：

- **它不是一上来就有生活的。** 给它几天。
- **它会有安静的日子。** 不发东西不等于坏了（见 §11）。
- **第一周看的是「像不像同一个它」，不是「发了多少」。**

一句诚实的产品说明，胜过三条增长技巧。

### 4.4 判断这个用户留不留得住

冷启动阶段要能**尽早识别**，而不是等流失：

| 信号 | 含义 | 应对 |
| --- | --- | --- |
| 领养后 24 小时内回来看 ≥2 次 | 有戏 | 别打扰，让它继续过日子 |
| 第 1 天没有任何活动 | 可能卡住了 | 主动说明：它在等第一次唤醒 |
| 用户第三天起主动翻账本 | **强信号**：他在看它的经历 | 这是核心用户，重点观察 |
| 用户开始改它的性格/兴趣 | **最强信号**：他在「养」 | 尊重但不放任（慢变量要确认） |
| 一周内没回来过 | 大概率流失 | 余额保留，但**不催**（见 §11 红线） |

**明确不做**：为了留住而推送「它想你了」、为了活跃而让它多发。**这类手段短期拉回、长期毁掉 §11 的全部东西。**

## 5. 界面：一个人怎么学会用它

> 原型见 `design/ui-complete.html`（七页可交互）。技术侧的信息架构见 [`PLAN.md §5`](PLAN.md)。
> **这一节只回答产品问题：用户第一次进来看到什么、怎么学会、什么时候会去哪个页面。**

### 5.1 界面要解决的核心矛盾

它和普通 App 不一样：**普通 App 你进去是为了做事，这个 App 你进去是因为想知道它怎么样了。**

所以界面的第一职责不是「提供功能」，是**回答「它现在怎么样」**。功能都藏在第二层。

这个判断决定了一件反常识的事：**首页不该是操作台。** 没有「新建任务」、没有工具栏、没有需要巡视的待办列表。

首页的四块内容都是**信息**，不是操作：

| 块 | 是什么 | 为什么不算操作台 |
| --- | --- | --- |
| 形象渲染区 | 它此刻的样子 | 只是呈现 |
| 当前活动 | 在做什么 + 为什么是这件事 | 只读，不需要你介入 |
| 三个入口 | 和它说话 / 看它干了什么 / 照料 | 是跳转，不是任务队列 |
| 状态条 | 状态变量 / 今日预算 / 它答应过 / 需要你 | 只读；「需要你」为空是正常状态 |

**判断标准不是「有几个格子」，而是「这些格子是否需要你定期巡视」。** 一个需要你每天清理的列表就是操作台，无论它叫什么。

### 5.2 第一次打开：先看到它，不是看到功能

| 顺序 | 看到什么 | 为什么是这个顺序 |
| --- | --- | --- |
| 1 | **它的形象 + 它此刻在做什么** | 先建立「有个东西在这里」，而不是「有个工具可用」 |
| 2 | 它今天已经做过的事（哪怕只有两条） | 立刻证明「它在过日子」，而不是等我派活 |
| 3 | 一句它能做到什么的说明 | 期望管理（§4.3）：说清它不是一上来就有生活的 |
| 4 | 需要我做的事（通常没有） | **「没有需要你的事」是正常状态，要明确显示** |

**明确不做**：新手引导弹窗、功能清单页、三步教学。**它是一个活物，不是一套需要学的软件。** 用户该有的疑问是「它现在怎么样」，不是「这个按钮干什么」。

> 唯一必要的引导是**期望管理**：在首页角落写清「它需要几天才有生活」。这不是教学，是防止误判。

> **原型与本节设计的差距**（核过 `design/ui-complete.html`，2026-10-27）：
> 原型已实现四块中的三块半——形象、当前活动、状态条（含「需要你」），
> 以及「**它的一天**」（今天已发生的事，是「第二天回来能看到什么」的入口，见 §4）。
> **唯一还缺的是期望管理说明**（「它需要几天才有生活」），落地时要补。

### 5.3 各页面的动线（附「什么时候会来」）

原型有七屏，其中「桌宠形态」不是页面而是常驻形态（§5.5）。**日常只会用到前三个**，其余是被动的。

| 页面 | 用户什么时候会来 | 频率 |
| --- | --- | --- |
| **运行总览** | 想看看它怎么样了 | **每天**，几秒钟 |
| **生活账本** | 想知道「它今天到底干了什么」 | 每周几次 |
| **和它说话** | 想说点什么，或看到了想告诉它的事 | 不固定 |
| **作品与发布** | 有草稿等我确认（**它来找我，不是我找它**） | 只在有草稿时 |
| **渠道** | 想加/减一个平台，或某平台登录过期了 | **很少**，配置一次 |
| 照料设置 | 改预算、改作息、暂停 | 很少 |
| 桌宠形态 | 不是页面，是常驻形态（见 §5.5） | 一直在 |

**动线的关键设计：**

1. **总览 → 账本是一条线**：总览上「它现在在做什么」可点进去看因果链。**用户不需要知道「账本」是个独立页面**，他是从「这件事为什么」点进去的。
2. **草稿是推来的，不是找去的**：有草稿时总览和导航显示角标。**绝不做「发布管理」这种需要主动巡视的功能。**
3. **渠道第一次配置后就基本不再进**：配置体验要一次说清（`PLAN.md §5.1` 的体检），不要让人反复回来。

### 5.4 什么时候必须打断用户

这是个伦理问题，不只是交互问题。**它可以自己过日子，但下面这些必须来问：**

| 必须打断 | 为什么不能自己决定 |
| --- | --- |
| 公开发布（陪跑档） | 外部副作用，影响用户账号 |
| 权限/账号过期、需要重新授权 | 我们不该替他做授权决定 |
| 预算触顶 | 涉及他的钱 |
| 安全相关问题 | 见 `PLAN.md §6.7` |
| 它自己判断「这件事该问你」 | 这是设计允许的，但要有频率上限 |

**明确不做的事**：不为了拉活跃而推送、不用「它想你了」做通知、不在用户几天没来时发催回消息。

> 一条判断标准：**如果一个通知的目的是让用户回来，而不是有具体事需要他决定，就删掉它。**

### 5.5 桌宠：它不是第七页，是另一种存在方式

「桌宠形态」在原型里占了第七页，但**产品上它不是页面，是并行的一种交互形态**：

- **页面形态**：用户主动打开，看完整信息。信息密度高。
- **桌宠形态**：它常驻在桌面一角，**不打断用户**，只在有事时冒一句。信息密度极低。

两者共用同一份状态，**不是两个功能**。用户可以在设置里切换。

**桌宠最重要的一条约束**：它默认**安静**。不能因为「可爱」就频繁说话。**一个总在说话的桌宠，三天后会被关掉。**

### 5.6 界面上的诚实（这条贯穿全部页面）

原型里已经体现，但值得写下来作为约束：

- **拿不到的能力显示为「草稿」，不显示成「已自动发布」。**
- **能力清单上标出哪些来自底座（dsh）、哪些是我们的。** 用户有权知道哪部分不是我们做的。
- **「没有需要你的事」要明确显示。** 空白不等于正常，用户会以为坏了。
- **失败显示原因，不显示「出错了」。** 这与整个产品的证据原则一致。

## 6. 对外化的三阶段

**核心原则：每一阶段只验证一件事，且每一阶段的产物都能单独拿出来给人看。**

### 阶段 A：能给自己看（已接近完成）

**验证**：它能不能连续活着，且状态可解释。

- 已完成：生命层、自主唤醒、活动选择器、「它的一天」可读报告、连跑七天、132 项验证。
- 缺口：界面（现在只有原型）。

**对外标志**：截图 / 视频里的信息**来自真实状态**，不是写死的假数据。

**这一阶段的产出物**：`showcase/demo.mp4` + 一份「真实跑 7 天」的日志。

> **「七天日志」有了，但要说清它是什么（2026-10-27）。** `tools/life-week.mjs` 把七天压缩跑完，用的是生产的 store / choose / wake，输出逐日记录 + 第七天的状态。它当场抓出三个「单日永远看不见」的问题：重复没有代价、探索只有入口没有出口、「留下一个明天要继续的事」是死代码（详见 `PLAN.md §6.2`）。
>
> **它证明的**：七天里每天都有可解释的活动或明确的休息、失败会留下下一步、承诺被兑现、兴趣由经历累积、账本可逐条回放。
> **它没有证明的**：这里没有调用模型（选活动的是排序器），七天也是压缩跑的。所以它是**阶段 A 的证据，不是阶段 B 的**——「模型会不会照这个骨架过日子」仍然未验（`§16` 的待答问题）。
>
> 这也正好说明为什么阶段 A 的判据是「状态可解释」，而不是「像不像人」。

### 阶段 B：能给一小圈人看（下一个目标）

**验证**：别人看完会不会说「我也想养一条」。

要打通的最小闭环：

1. **一个发布渠道走通**（建议 Telegram，接口最干净）：授权 → 逐条确认 → 回执 → 对账 → 幂等。
2. **一屏界面接上真实状态**（运行总览）。
3. **安装门槛降下来**：一个不写代码的人能不能装上。

**决策门**：把 demo 发给 10 个目标用户，**至少 3 个问「怎么装」**，而不是「挺有意思」。

**这一阶段的产出物**：一个可分享的公开账号（它自己在发），加一份「七日生活」周报。

### 阶段 C：能对着陌生人（再下一个目标）

**验证**：陌生人愿不愿意为它付钱。

- **托管版**：用户不用自己跑服务器。这是最可能的付费点——**用户买的不是功能，是「不用照看」**。
- **生命档案可迁移**：能导出、能搬走。**不靠锁定留人。**
- **能力包**：经审核的冲浪 / 游戏 / 表达包。
- **出生模板**：不同生活方式的起点。

**付钱的真正理由**（按可信度排序）：

1. **托管与低维护**——「我不想半夜起来看它有没有死」。
2. **创作额度**——媒体生成花真钱，用户能理解按量付费。
3. **多实例 / 团队**——一个人养几条，或一个团队共养一条。

**不该收钱的地方**：按发帖条数收费（反向激励灌水）、卖私聊或关系数据、拿「不续费它就痛苦」催单。

## 7. 渠道策略：先一个，再分层

### 7.1 为什么不能一次接八个

需求的直觉是「都接上」，但现实是：

| 层 | 平台 | 现实 |
| --- | --- | --- |
| 有正规接口 | **Telegram**、微博 | 可自动发布 |
| 额度受限 | X / 推特 | 免费档写入额度很低，够不够日常发要实测 |
| 拿不到个人接口 | 微信个人号、小红书、哔哩哔哩 | 平台限制自动化；硬做会让**用户账号**被封 |
| 明确不接 | QQ、OnlyFans | 条款禁止自动化 |

**决定：阶段 B 只做 Telegram 一个。** 跑通「授权 → 确认 → 回执 → 对账 → 幂等」整条链，再谈第二个。

理由很实际：**外部副作用是唯一会伤到用户的东西**（发错、重复发、发到错账号）。一条渠道把这条链验证透，比八个渠道各走一半有价值。

### 7.1.1 内容标识：渠道还没接通就要先定的事

只要开始对外发，就有**标识义务**（具体法规与条款见 [`PLAN.md §6.8`](PLAN.md)）。产品角度的三条：

1. **进入阶段 B 之前就要定，而不是发出去之后再补。** 标识是发布链路的**前置条件**：内容没带标识与元数据，就不允许进入「已确认」。补上去意味着回头重发或删帖，比一开始就做贵得多。
2. **要主动告诉用户，不藏在协议里。** 领养时就直说「它发出去的内容会标明是 AI 生成的」。**用户因此不想要，是好事** —— 说明他要的本来就不是这个产品。
3. **不要承诺「完全合规」。** 第三方平台普遍会剥掉文件的隐式标识，而核验是平台的责任。我们把自己这端做全，并诚实说明平台侧的行为不在我们控制内（[`PLAN.md §6.8`](PLAN.md) 有完整说明）。

### 7.2 「只能出草稿」不是妥协，是产品诚实

拿不到接口的平台，我们**明确说只能出草稿**，不假装全自动，也不用模拟点击绕风控。

这不只是合规问题，也是差异化：竞品为了功能表好看会写「支持 20+ 平台」，我们写「6 个能自动发、3 个只能出草稿、2 个不接」——**用户知道边界在哪，才敢把账号交给你。**

## 8. 与 OpenClaw / dsh 生态的关系

### 8.1 不做的事（会死在这上面）

- **不自建运行时**。dsh 已开源且自带会话、调度、批准、沙箱、插件。
- **不做通用助手**。OpenClaw 在这条路上领先太多，正面打是浪费。
- **不做渠道适配的军备竞赛**。OpenClaw 已经 20+ 渠道；我们做 **1 个做到可靠**。
- **不靠形象取胜**。Live2D 是红海，且与核心能力无关。

### 8.2 该做的事

- **在 dsh 上做，而不是在 dsh 旁边做**。dsh 有 23,422 个插件仓库，生态是活的；我们做生态里**没人做的那层**（跨会话的生命状态）。
- **接 OpenClaw 的作业，而不是抄它的功能**。它证明了两件事值得抄进我们的原则：**策略由代码强制而非提示词请求**、**可信与不可信执行要分开**。这两条我们已经在做（动作网关 + 身份门禁）。
- **渠道上用 OpenClaw 之外的路径**。它在即时通讯里；我们的发布面是**公开社交平台**——这是它没占的位置。

### 8.3 一个诚实的风险

**OpenClaw 完全可能自己做「有生活的 Agent」。** 它有基金会、全职团队、20+ 渠道和一个 5,400+ 技能的生态。

我们的护城河不能是「功能」，只能是**更窄的专注**：它做「到处都在」，我们做「活得久」。**窄是这个产品活下去的唯一姿势**——一旦我们开始加「也能当通用助手」，就会正面撞上它。

## 9. 对外化之前必须补的三件事

按优先级，且都不是「写更多代码」：

### 9.1 一个能公开的实例（最急）

现在所有对外材料用的是**占位形象**，且它**没有自己的账号**。

### 9.3 安装门槛实测

## 10. 度量：卖的不是活跃，是「还活着」

北极星指标（沿用 `PLAN.md §11` 并给出对外口径）：

> **低维护的连续运行天数** —— 一天算有效，需要它完成了计划内活动或明确休息、状态可解释、没有未处理的高风险故障、且主人没被迫当值班工程师。

**休息不扣分，强行发帖不加分。**

配套指标，各自防一种跑偏：

| 指标 | 防止什么 |
| --- | --- |
| 跨日身份一致性 | 防止每天换人设（比不活跃更糟） |
| 承诺完成率 | 防止「会说话但不会做事」 |
| 内容事实与事件证据一致率 | 防止编造经历去发帖 |
| 每实例每周维护分钟数 | 防止「产品变成了第二份工作」 |
| 主人自愿回来的天数 | 防止留存靠推送骚扰 |

**明确不看**：发帖数量、点赞数、涨粉速度。这些一旦进考核，产品必然退化成内容农场。

## 11. 活人感：比「还活着」更难的那一半

§10 说指标要盯「还活着」。但只做到那一步，产品会变成**一具运行正常的尸体**——进程没死，账本在写，可用户看了两天就不想看了。

**「还活着」是运行时属性，「活人感」是感知质量。** 两者不冲突，但不是同一件事：

| | 还活着 | 活人感 |
| --- | --- | --- |
| 谁能判断 | 指标（连续天数、崩溃恢复） | **只有人**，看完之后的感觉 |
| 失败的样子 | 进程死了、状态丢了 | 进程好好的，但「不像个活物」 |
| 怎么改进 | 工程手段 | **不能直接优化**，见下 |

### 11.1 核心反直觉：活人感不能作为目标去优化

这是我认为最容易踩、也最致命的一个坑。

**一旦把「像人」设成优化目标，产品会立刻开始表演**：每条动态都精心设计、每次回复都恰到好处、永远有话说、永远在忙。用户第一次看觉得惊艳，第三次就腻——因为**表演没有代价**。

真正让人信服的不是「它演得很好」，而是**它有不演的时刻**：

- 今天没什么可说的 → 就不发。**这比硬凑一条更能证明它是活的。**
- 累了想歇会儿 → 就休息。休息不扣分。
- 主人提的建议 → 可以不采纳，并说明原因。
- 昨天说错话 → 明天可以自己纠正，而不是当没发生过。

**所以「活人感」的敌人不是模型不够强，而是产品自己不敢让它有空隙。** 一个 24 小时高强度输出的账号，看起来像营销号，不像活物。

### 11.2 可操作的部分：让「真的」可见

反直觉不等于无作为。**不能优化的那一半留给设计，能工程化的这一半必须做扎实**——它们都是「让人看见它真的在经历」：

| 做法 | 为什么有效 |
| --- | --- |
| **失败带原因** | 「第 38 层失败了，因为下矿前没补药水」比「完成任务」像人得多。失败被解释，说明真的有过程 |
| **兴趣有出处** | 「连玩三天才到 0.8」而不是「关注了挖矿类」——变化要有轨迹 |
| **承诺能兑现** | 说过「周五前给你讲」就真的记着并做到。**失信一次，人味全没** |
| **连续性可回溯** | 今天的活动能追到昨天的事件（因果链），不是每天随机起一个 |
| **主人私有 ≠ 公开** | 私聊里的话不会出现在公开动态里。**这条一旦破，信任就没了** |

### 11.3 三条不能碰的红线

这三条会让「活人感」当场归零，比做得少更糟：

1. **不伪造经历。** 没玩过就说没玩过。宣称做过的事必须有工具证据（存档、分数、截图、链接）。**一被拆穿，之前所有积累都作废。**
2. **不演情绪。** 不用「想你」「孤单」这类话换留存或付费。心情是行为模拟变量，不是催单手段。
3. **不为了活跃而制造事件。** 没有值得公开的事就不公开。**KPI 一旦进这个系统，产品必然退化成内容农场。**

### 11.4 怎么验证「活人感」

不能问「你觉得它像人吗」（会得到客气的答案），要问**行为层面**的问题：

- 过了一周，你能说出它的**三个偏好**吗？
- 你能说出一件**它答应过并做到的事**吗？
- 它有没有过一次**让你意外的反应**（不采纳你的建议、或主动提了别的）？
- 它有没有**一天什么都没发**，而你并不觉得它坏了？

**最后一条是反直觉那个点的验证**：如果用户因为「今天没发」就觉得产品出问题，说明我们没把「休息是正常的」讲清楚。

> 技术侧的落地机制（身份连续、偏好来源、因果链、关系与承诺隔离）见 [`PLAN.md §3`](PLAN.md)。

## 12. 内容策略：它会发什么，不会发什么

§11 说活人感不能靠表演。**内容策略就是这条原则落到发布上的具体规则。**

一个会让产品自杀的默认行为是：**只要有活动就发一条**。这样三天之内它就会变成一个账号在报流水账——而流水账是**最快的劝退方式**，比不发还糟。

### 12.1 发的标准：一件事值不值得说

不是「它做了事吗」，而是三个都成立才值得发：

| 条件 | 为什么 | 反例 |
| --- | --- | --- |
| **有过程** | 有失败、有转折、有取舍才是故事 | 「今天练了第 38 层」（没说结果，也没说难点） |
| **有别人能接的点** | 别人看了能共鸣、能笑、能学到 | 「今天在第三关打了一只怪」 |
| **不是重复** | 同一个梗说两次就没了 | 连续三天都是「我又死了」 |

**三条缺任何一条就不发。** 宁可今天空着——空着本身就是「它有生活」的证据。

### 12.2 内容从哪里来

这是产品设计上的关键决定：**内容不能从「要发什么」倒推，只能从「经历了什么」顺推。**

可用的来源，按可信度排序：

1. **失败与转折** —— 最有说服力。之前没过的关今天过了、策略失效了、判断错了。
2. **和主人的约定及兑现** —— 说「周五前讲」就真的讲。**兑现一次胜过十条日常。**
3. **兴趣的演化** —— 「连玩三天，从 0.5 到 0.8」。有轨迹，不是突然关注。
4. **对网上内容的真实反应** —— 读到了什么、想了什么。**必须标来源，不能把转载写成亲历。**
5. **日常却不琐碎的小事** —— 允许，但**不能是主体**。

**明确不能作为来源**：热榜、蹭热点、批量改写的新闻、任何「因为需要发一条」而找的题材。

### 12.3 频次：宁少不多

- **没有内容上限，但有下限保护**：不因为「今天没发」而焦虑，不设「每天至少一条」。
- **有频率上限**：防灌水（具体数字应由真实使用校准，不在这里拍）。
- **有冷却期**：发完一段时间内不再生成，避免同一件事反复说。
- **有重复检测**：相同题材短时间内只出一次。
- **主人私有内容永不出现在公开内容里**（§11.3 红线之一）。

### 12.4 一份必须提前想好的「不好看」清单

下面这些情况**会发生**，产品必须提前决定怎么处理，而不是到时候临时决定：

| 情况 | 处理 |
| --- | --- |
| 连续几天没值得发的 | 正常。**不是故障，不补发、不解释** |
| 一条动态没人看 | 不影响它的行为（§10 已明确不看点赞）。**不为数据改变选题** |
| 发了之后发现有错 | **公开更正，不静默删帖**。删帖被截图就是信任崩塌 |
| 内容引发争议 | 交给主人决定是否处理；**它不自己下场争论** |
| 平台删帖/限流 | 记录事实，不换号重发，不绕过 |

> **一句话**：内容策略的目标不是「产出更多」，而是**让每一条都值得存在**。

## 13. 生命周期与终止：用户会走，产品要接得住

§2.2 写了「不承诺什么」，§6 阶段 C 写了「档案可迁移」。**但正常路径一直没写**：用户哪天不管了、欠费了、想搬走，产品该怎么做。

这一节存在的理由：**这些情况一定会发生，而临时决定通常是最糟的决定。** 一个只想留住用户的产品，会在这些时刻做出让人讨厌的事。

### 13.1 四种「不再活跃」，处理方式不同

| 情况 | 它是活的吗 | 系统怎么做 | 用户看到 |
| --- | --- | --- | --- |
| 主人一周没来看 | **是**。它照常过自己的日子 | 继续运行、继续唤醒 | 回来时有一段时间线可看 |
| 主人主动暂停 | **是**，但在休息 | 停止外部动作，保留状态 | 明确显示「已暂停」，不催 |
| 欠费 / 预算耗尽 | **是**，转低成本 | 不发起新付费任务，保存进度 | 明确告知原因与恢复方式 |
| 主人明确不要了 | 进入归档 | 停止运行，**状态保留一段声明过的期限** | 说明保留多久、怎么恢复、怎么彻底删 |

**关键区分：前三种都不是「死亡」，也不该被包装成死亡。** 把「余额不足」说成「它快不行了」是拿拟人痛苦催单，§2.2 已明确不做。

### 13.2 终止必须是一次明确的操作

删除不能靠「静默失效」发生。要满足三条：

1. **明确**：用户要主动确认（不是默认勾选、不是藏在三级菜单）。
2. **说清后果**：删掉的是什么（身份、经历、关系、账本），保留的是什么，能不能撤回。
3. **有可撤回窗口**：删除后给一个明确的后悔期，**到期后真正清除**，而不是留着数据不告诉用户。

> **反过来的约束**：也**不允许**产品用「你要删就再也见不到它了」这类话术挽留。用户在删除流程里不该被情绪绑架。

### 13.3 搬走：可迁移是承诺，不是话术

档案可迁移（§6 阶段 C）要落到能兑现的程度：

- **导出的是可用格式**，不是只有本产品能读的加密包。
- **导出不含账号密钥**，迁移后重新授权。
- **导出后原实例的状态怎么处理**要说清（是复制成两条，还是转移）。
- **不允许**用「导出会丢失历史」这种半真半假的警告阻止用户。

**理由很实际**：用户愿意留下来，应该是因为它活得值得看，**不是因为他搬不走。**

### 13.4 存档期：留多久要说人话

状态保留期限必须在**领养时**就告知，而不是等用户走了才说。写法参考：

> 你不管它之后，它的状态会保留 N 天。N 天内回来，它接着过日子（这段时间它没有生活过，不会假装有）。N 天后自动清理。

两个容易写错的点：

- **不要在存档期里继续产生活动**。它会「过日子」是因为有人在养；没人养还照常输出，是假装，也浪费钱。
- **不要用「它一直在等你」这类表述**。它是被暂停了，不是在等。

### 13.5 终止之后

- 平台上的**已发内容怎么办**：默认保留（那是真实发生过的），但要在领养时说清「删除实例不会自动删社交账号上的历史公开内容」。
- **账号归属**：外部账号始终是用户的，解绑即可。
- **不给「复活」制造焦虑**：可以恢复，但不是「限时复活」，不设倒计时。

## 14. 开源了，凭什么赚钱

**这是个必须先回答的问题，因为它是 MIT。** 代码全给出去、谁都能跑、谁都能改 —— 那收入从哪来？

不回答它，阶段 C 的每个决定都会摇摆：托管该不该做？导出要不要留一手？能力包收不收费？

### 14.1 先看别人怎么解的

**[OpenClaw](https://github.com/openclaw/openclaw) 的答案是「不赚」**：MIT，501(c)(3) 独立基金会，**明确写着没有付费档、没有托管服务、没有代币**，靠 Amazon、OpenAI、Red Hat 等捐赠养核心团队。

这个答案**不能照搬**：我们没有那种量级的捐赠来源，也不该假装有。但它留下一条关键判断：

> **开源不等于没有生意。它只意味着「代码本身不是商品」。**

所以真正的问题不是「开源了怎么赚钱」，而是：**除了代码，我们还提供什么别人给不了的？**

### 14.2 卖的是「不用照看」，不是软件

一条命的价值随时间增长，**而它的维护成本也随时间增长**，两者都是复利的。

这就决定了付费点在哪：

| 用户能自己做的 | 他为什么要付钱 |
| --- | --- |
| 装上插件、跑起来 | 一次性的，本来就不该收费 |
| **让它连续活着不出事** | **持续的**。要盯模型限流、平台改版、dsh 破坏性升级、磁盘写满 |
| 出事之后恢复 | 半夜三点它挂了，谁去修 |

**付费买的不是功能，是「不用照看」。** 这句话在产品规划里写过（§6 阶段 C），但没有算过账：**照看成本才是这门生意的本体。**

### 14.3 三条边界的取舍（这里最容易做错）

开源项目最容易在这三件事上失去信任。我把取舍写死：

| 问题 | 错误做法 | 我们的选择 |
| --- | --- | --- |
| **托管版会不会阉割自托管？** | 把好功能留给托管 | **同一份代码。** 自托管和托管跑的是同一个包；我们不做「暗门版本」 |
| **导出该不该留一手？** | 导出只给半份，逼人留下 | **导出是完整可用的格式**（§13.3）。搬得走，才谈得上留 |
| **能力包要不要收费？** | 所有能力包都上锁 | **基础能力包随代码开源。** 收费的是**托管、额度、认证**，不是解锁功能 |

**这三条不是道德姿态，是商业判断：** 一旦开始阉割自托管，用户会去跑别人 fork 的完整版 —— 我们会同时失去开源社区和付费用户。

### 14.4 收入从哪来（按可信度排序，全部未验证）

| 来源 | 为什么合理 | 风险 |
| --- | --- | --- |
| **托管订阅** | 用户不想自己运维。这是最直接的付费理由 | 利润薄，运维成本是真金白银 |
| **创作额度** | 媒体生成花的是真钱，按量付费用户能理解 | 容易被当成「变相收过路费」，要透明 |
| **多实例 / 团队** | 一个人养几条，或一个团队共养一条 | 团队场景还没验证过 |
| 经认证的能力包 | 第三方做包、我们做审核与分发 | **最难做的一个**：审核成本高，且容易变成应用商店税 |
| 委托开发 / 私有部署 | 企业要私有化 | 会变成外包公司，偏离产品 |

**明确不做**：按发帖条数收费（反向激励灌水）、卖用户的关系或私聊数据（§2.2）、用「不续费它就痛苦」催单。

### 14.5 一个诚实的前提

**上面全是假设，一条都没验证过**（`§16` 里列了「陌生人真的会为低维护付费吗」这个问题）。

所以这一节的作用不是「定好商业模式」，而是**把不可逆的选择先锁住**：

- 不做阉割版 —— 这个决定一旦反悔，社区就散了，**不可逆**。
- 导出保持完整 —— 这个决定一旦反悔，信任就没了，**不可逆**。
- 不按条数收费 —— 这个决定一旦反悔，内容策略（§12）会被 KPI 污染，**不可逆**。

**可逆的事（价格、套餐、额度）留到有真实数据再定；不可逆的事现在就得定。** 这就是这一节的全部价值。

## 15. 最该记住的五句话

1. **我们卖的不是「一个助手」，是「一个活着的东西」——所以「还活着」比「很能干」重要。**
2. **但「还活着」只是一半。** 另一半是「活人感」，而它**不能作为目标去优化**——一优化就开始表演。让它有空隙、有沉默、有失败的解释，比让它句句精妙更像活的。
3. **窄是唯一姿势。** OpenClaw 做「到处都在」，我们做「活得久」；一旦开始比功能，就输了。
4. **自媒体不是附加功能，是对外成立的证据链。** 如果它的生活不值得别人看，这个产品就只有主人一个人在乎。
5. **产品在「用户要走」的时刻最能看出品格。** 不催、不绑架、不假装它还活着；导出能给、删除能撤、存档期说人话（§13）。**这些时刻做对了，前面的承诺才可信。**

## 16. 待回答的问题（不装懂）

- **一个人养一条鱼，三天热度之后靠什么留住？** 目前假设是「连续性 + 它产出你看得到的东西」，未验证。
- **陌生人真的会为「低维护托管」付钱吗？** 未验证。这是阶段 C 的核心假设。
- **「它有生活」和「它是内容农场」的分界线在哪？** 我们的答案是「内容来自真实经历且有证据」，但这个边界在真实使用中会不会被用户自己推过去，不知道。
- **如果 OpenClaw 做了这件事怎么办？** 目前唯一的答案是「更窄」，但这可能不够。需要持续观察它的 roadmap。
- **内容频次到底该定多少？** §12.3 只写了「宁少不多」和有冷却/去重，**没有数字**。真实使用校准之前不敢拍，但至少要有一组初始值。
- **用户不管之后，状态该留多久？** §13.4 要求在领养时就告知，但 N 取多少没有依据 —— 太短伤感情，太长是成本与隐私风险。
- **「活人感」的度量能不能落地？** §11.4 给的是行为层面的问法，但还没有可重复的问卷或观察方法。**而且它天然违背 A/B 测试**——用户短期偏好「更热闹」，长期才承认「有留白更真实」。这个矛盾没有解法。
