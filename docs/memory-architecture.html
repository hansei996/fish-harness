记忆架构：两侧各层怎么维护记忆，以及怎么跨对话

dsh 让一个 Agent 活过一次对话；Fish Harness 让它活过一次重启。 关键在于两者的作用域不同 —— dsh 的会话按「目录 + 会话 id」分桶， Fish 的生命按「lifeId」分桶，与目录、与哪次对话都无关。 下面所有路径都是实跑 dsh 之后从磁盘上读出来的，不是设计稿。

一、跨对话是这么发生的

dsh 的会话日志到会话结束就不再增长 —— 这是一个真实的断层。 跨过这个断层的，只有 Fish 层那份与对话无关的状态。

会话 N一次对话
dsh · agent-loop
跑一轮

读会话日志 → 组装提示词 → 调模型 → 执行工具 → 写回

dsh · 会话级
session.v4.jsonl.zstd

按「项目路径 / 会话 id」分桶（源码 projectDir(root, cwd) → projectKey(cwd)）。 事件溯源：turn/start、step/end、user/message… 实测一份 20 个事件、压缩后 18.9 KB。

会话结束 · 日志停止增长
会话 N+1下一次对话 / 下一次自己醒来
dsh · agent-loop
新跑一轮

对 dsh 而言这是一次全新的会话，日志是空的

dsh · 会话级
一份新的会话日志

但这一轮的系统提示词里，多了一段「它是谁、昨天做到哪」

Fish Harness · 生命级 —— 横跨两个会话，不断
life/<lifeId>/

identity.json traits.json relations.json commitments.json activity.json wake.json ledger.jsonl outbox.json
新一轮开始时，它把「我是谁 / 在做什么 / 下一步 / 最相关的 5 个兴趣 / 最紧的 5 个承诺」 作为一段 systemPrompt section 注入 —— 实测 682 字节，且不随寿命增长。

二、两侧各层各维护什么

DeepSeek Harness会话级 · 按目录+会话分桶
  • 会话与恢复sessions/<项目>/<会话id>/session.v4.jsonl.zstd 事件溯源 + zstd；另有 session.lock 做进程锁。 目录名由 projectDir(root, cwd) 推出，路径里的 / 用 encodeSegment 转义（所以看到的是 --Users-…--）
  • 格式迁移session-format + v0→v1→v2→v3→v4 四个迁移包 —— 旧日志升级后仍能读，这是它敢长期存的前提
  • 投影缓存storages/session_projcache/sessions/*.json 可重建的加速层，不是事实源
  • 持久目标goal 包（create/complete/pause/edit） 按会话生命周期管理
  • Host 级定时schedule —— 到点投一条消息，进程不常驻也能补投
  • 检索与统计session-query-sqlite、session-search、session-stats
  • 凭据与沙箱credentials（.credentials.yaml）、sandbox、approval
Fish Harness生命级 · 按 lifeId 分桶
  • 它自己补的那层：dsh 没有「跨会话仍然成立的个体」， 所以这一层只做那一件事
  • 极慢identity.json —— 名字、性格种子、版本号。 只有主人确认能改（能改人格的注入 = 能换人）
  • 慢traits.json 兴趣·技能（带置信度与来源）、 relations.json 认识谁、commitments.json 答应了什么
  • 快activity.json 此刻在做什么 + 给下一步的交接、 wake.json 下一个闹钟与预算
  • 只追加ledger.jsonl —— 唯一可回放的记录； 其他文件都能推导，它不能
  • 外部副作用outbox.json 发布状态机 —— 单独设计，因为日志解决不了「发出去没有」
  • 不重写 dsh 的任何一件：会话、调度、沙箱、批准、工具注册全部复用

三、记忆按「变化速度」分三层

混在一起是长期运行最先崩的地方 —— 更新权限不同，速度也不同。

极慢只有主人能改
  • identity.json 名字 · 性格 · 版本号
  • 改它需要显式确认，一次网页注入改不动
慢由经历累积
  • traits.json 兴趣 · 技能（带置信度）
  • relations.json 主人 / 公开分开存
  • commitments.json 承诺与到期
  • 「连玩三天才升到 0.8」，不是收藏一下就变
快每轮都在动
  • activity.json 当前活动 + 下一步交接
  • wake.json 闹钟 · 预算 · 已投递 id
  • ledger.jsonl 追加式账本
  • outbox.json 发布状态机

四、磁盘上真实长这样

下面这棵树是启动一个真实 dsh profile 之后 find 出来的，不是画的。

$DSH_HOME/ ├── sessions/ ← dsh：会话级，按项目路径分桶 │ └── --Users-you-myProject--/ ← projectKey(cwd)：换个目录=另一批会话 │ └── session-<uuid>/ │ ├── session.v4.jsonl.zstd 事件溯源 + zstd 压缩 │ └── session.lock 进程锁（这层我们没有） ├── storages/session_projcache/sessions/ ← dsh：投影缓存，可重建 ├── profiles/<name>/ ← dsh：profile 定义 │ ├── cordis.yml · cordis.patch.yml │ └── package.json · pnpm-workspace.yaml ├── .credentials.yaml ← dsh：凭据（不进模型上下文） └── life/ ← Fish：生命级，与目录/会话都无关 └── default/ （lifeId，不是会话 id） ├── identity.json 极慢 · 只有主人确认能改 ├── traits.json 慢 · 兴趣/技能 + 置信度 ├── relations.json 慢 · 认识谁 ├── commitments.json 慢 · 答应了什么 ├── activity.json 快 · 现在做什么 + 下一步 ├── wake.json 快 · 下个闹钟 · 预算 ├── ledger.jsonl 只追加 · 唯一可回放 └── outbox.json 外部副作用状态机
断层就在这里。 sessions/ 那一支到会话结束就不再增长，而 life/ 这一支从来不看会话 —— 所以「下一次对话」对 dsh 是全新的，对这条命却只是又一天。 这也是为什么它必须落成文件：放进内存或会话里，重启就没了。

五、为什么这样就能长期自己跑

四条机制（都实测过）
  • 每次写原子先写 tmp 再 rename → 断电时磁盘上要么旧内容、要么新内容，永远不会是半截 JSON
  • 每次读容忍坏文件实测 identity.json 截断 → 读到 null 不抛错； 账本尾部半行 → 跳过照读。一条坏文件不该弄死一条命
  • 账本懒裁剪写 500 条(cap=100) → 401 → 216 条。 在 cap/2 ~ cap×2 之间震荡是有意的 —— 每次追加都重写整个文件会让长跑变慢
  • 上下文有界每轮只注入 682 字节且不随寿命增长。 这是「长期养得起」和「养不起」的分界线
它自己会醒（不靠人叫）
  • 接 dsh 的 schedule每轮结束补一个一次性闹钟，进程不常驻也能补投
  • 抖动every ± jitter，不会每天同一秒醒
  • 静默时段默认 23:00–08:00 不打扰
  • 每日预算默认 6 次，按 messageId 幂等记账（dsh 不保证 exactly-once）
  • 不整天消失目标被静默推到「后天」时夹回被跳过那天最后一个允许时刻 —— 这条是 soak 抓出来的（曾出现 34 小时空窗）
  • 明天还记得昨天失败留下 activity.next，下次醒来读得到。 这条曾经是死代码：有读的分支，没有写的路径
这张图证明什么、没证明什么。 图中所有路径都是启动真实 dsh profile 后从磁盘读出来的（会话事件数、压缩后大小、目录分桶方式均为实测）； 「四条机制」有对应断言（verify/smoke.mjs、verify/life-week.mjs、verify/publish.mjs）。 完整方案见 docs/MEMORY.md。

它没有证明的：长期记忆会不会「糊」—— 跑三个月要不要总结、怎么总结，未验证； 跨进程没有锁（dsh 有 session.lock，我们这层没有）； 真实长跑也没做过（七天是压缩跑的，没有真实等待）。
