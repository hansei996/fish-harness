记忆层架构：为什么它能长期自己跑

dsh 让一个 Agent 活过一次对话；记忆层让它活过一次重启。 后者是状态问题 —— 进程会退、手机会关机、dsh 会升级。 会话没了可以重开，状态没了它就变成另一个人。

会话持久化、崩溃恢复、Host 级定时、后台作业、逐次批准、进程隔离 —— 这些它已经做完了。记忆层不重写其中任何一件，只用它的公开扩展点。

二、四条让它「不养死」的机制（都实测过）

① 每次写都是原子的

先写临时文件，再 rename。断电时磁盘上要么是旧内容、要么是新内容，永远不会是半截 JSON。

tmp + rename

② 每次读都容忍文件坏掉

截断的 JSON 不抛错，降级成 null；账本尾部有半行就跳过。一条坏文件不该弄死一条命。

identity.json 被截断 → 没崩，读到 null

③ 账本有上限，而且是懒裁剪

写满阈值才收，收到一半 —— 于是它在 cap/2 ~ cap×2 之间震荡而不是精确停在 cap。每次追加都重写整个文件，会让长跑实例越来越慢。

写 500 条 → 401 → 收到 216 条

④ 每轮注入的上下文有界

只给「此刻该知道的」：我是谁、在做什么、下一步、最相关的 5 个兴趣、最紧的 5 个承诺。

13 个字段 · 682 字节 · 不随寿命增长

三、为什么这就能长期自己跑

✕ 如果每轮塞进全部记忆

token 随寿命线性增长 —— 跑三个月就贵到用不起。而且越长越慢、越贵，最终只能是「养不起」而不是「养不死」。

✓ 每轮只付固定的一小笔

682 字节，第 1 天和第 300 天一样。要更多时它自己去查（life_ledger）。这是长期可运行的关键取舍。

它自己会醒

每轮结束向 dsh 的 schedule 补一个一次性闹钟。抖动 / 静默时段 / 每日预算 / 不整天消失 —— 四条策略在 lib/wake.js，纯函数，可确定性测试。

不整天消失：34 小时空窗是 soak 抓出来的

明天还记得昨天

失败时留下一条下一步（activity.next），下次醒来在快照里读得到 —— 这是数据上的事实，不是提示词里的请求。

这条曾经是死代码：有读的分支，没有写的路径

外部副作用单独管

sending 先落盘再发 —— 崩在中间，磁盘上是「可能已发」而不是「从没发过」；unconfirmed 没有自动重试路径。

Telegram 无幂等键、无法反查 → 这一步必须由人

四、不做的事（也是为什么它简单）

不引数据库

单实例状态量小。引入 DB 会把「装一个插件」变成「部署一套服务」。

不把向量库当唯一事实源

检索索引可以重建，账本不可。能重建的东西不能是权威。

不复制对话历史

那在 dsh 的 core/session 里；复制会带来两套不一致。

不让猜想自动变事实

摘要与候选变更可以自动生成，但提升为事实需要显式动作。
