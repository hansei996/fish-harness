# 记忆层技术方案：为什么它能长期自己跑下去

> 这份文档讲一件事：**它凭什么在没人管的情况下，几个星期后还是同一个它。**
>
> 面向实现，每条都指到代码；数字来自 `node tools/facts.mjs`（唯一权威来源），不是抄的。
> 总览图见 [`docs/memory-architecture.html`](memory-architecture.html)。

---

## 1. 一句话

**dsh 让一个 Agent 活过「一次对话」；记忆层让它活过「一次重启」。**

这两件事的难度完全不同。前者是会话问题，后者是**状态问题**：进程会退、手机会关机、
dsh 会升级、平台会改接口。会话没了可以重开，**状态没了它就变成另一个人**。

所以记忆层不存「对话历史」—— 对话历史在 dsh 那里。它存的是**跨会话仍然成立的事实**。

---

## 2. 八个状态文件，按「变化速度」分层

这是整个设计的核心，不是一个数据库表。八个文件各自的**变化速度**不同，
更新权限也不同 —— 混在一起是长期运行最先崩的地方。

| 文件 | 存什么 | 变化速度 | 谁能改 | 为什么单独放 |
| --- | --- | --- | --- | --- |
| `identity.json` | 名字、性格种子、表达风格 | **极慢**（版本号 `revision`） | **只有主人确认** | 一条网页注入改不动它；能改人格的注入 = 能换人 |
| `traits.json` | 兴趣、技能（带置信度与来源） | 慢 | 经历累积 | 「连玩三天才升到 0.8」，不是收藏一下就变 |
| `relations.json` | 认识谁（主人 / 公开分开） | 慢 | 遭遇 | 私聊关系不会因为要发帖被检索 |
| `commitments.json` | 答应了什么、什么时候到期 | 慢 | 承诺 / 兑现 | 承诺是它「明天还想继续」的拉力来源 |
| `activity.json` | 此刻在做什么 + **留给下一步的交接** | 快 | 每轮 | 同时只允许一个主活动 |
| `wake.json` | 下一个闹钟、当天预算、已投递的消息 id | 快 | 调度 | 幂等记账：dsh 不保证 exactly-once |
| `ledger.jsonl` | 追加式事件账本（唯一可回放的记录） | 只追加 | 只追加 | 其他文件都可推导，账本不可 |
| `outbox.json` | 发布状态机（草稿→已发/待确认） | 快 | 发布线 | 外部副作用不能靠日志解决 |

> 对应实现：`lib/store.js` 构造函数的 `this.files`（8 个路径）。
> 账本目前有 **12 种** kind，从 `born` 到 `publish`。

## 3. 四条让它「不会养着养着就死了」的机制

这四条都是**实测过**的，不是设计意图。

### 3.1 每一次写都是原子的（tmp + rename）

```js
const tmp = `${file}.tmp-${process.pid}-${Date.now()}`
fs.writeFileSync(tmp, JSON.stringify(value, null, 2))
fs.renameSync(tmp, file)          // rename 在同一文件系统上是原子的
```

**为什么关键**：在写到一半时断电/被 kill，磁盘上要么是旧内容、要么是新内容，
**永远不会是半截 JSON**。这是「养不死」的地基 —— 没有它，一次意外断电就可能让它变成另一个人。

### 3.2 每一次读都容忍文件坏掉

实测（`identity.json` 被截断成 `{"name":"半截`）：

```
✓ 没崩 —— readIdentity() 返回 null（降级），其余状态照常可用
✓ 账本尾部有半行 → 跳过后照常读回 216 条
```

**为什么不抛错**：一条截断的 JSON 不该弄死一条命。读写在 `readJson` / `readJsonl` 里
逐行 try/catch，只跳过坏的那部分。

### 3.3 账本有上限，而且是「懒」裁剪

```
阈值 = cap × 200字节 × 2      触发后才收，收到 cap 的一半
cap = 20000（默认）
```

实测：写 500 条（cap=100）→ 401 条 → 触发裁剪 → **216 条**。

**这不是 bug，是有意的**：每次追加都重写整个文件，会让长跑的实例越来越慢。
所以它在 `cap/2 ~ cap×2` 之间**震荡**，而不是精确停在 cap。
裁剪本身是 best-effort：裁剪失败绝不能让一次写入失败。

### 3.4 每轮注入的上下文是**有界**的

这是长期运行里最容易被忽略的成本：如果每轮都把全部记忆塞进提示词，
**token 会随寿命线性增长**，跑三个月就贵到用不起。

实测：灌入 200 个兴趣 + 200 条承诺后，快照是

<!-- facts:memory-snapshot -->
```
13 个字段 · 648 字节 · 兴趣取前 5 · 承诺取前 5
```
<!-- /facts:memory-snapshot -->

**它不随生命长度增长。** 只给「当前该知道的」：我是谁、此刻在做什么、
下一步是什么、最相关的 5 个兴趣、最紧的 5 个承诺。

> **这是长期可运行的关键取舍**：不是记得越多越好，而是**每轮只付固定的一小笔**。
> 需要更多时模型可以主动调 `life_ledger` / `life_whoami` 去查。

## 4. 为什么这就能「长期自己跑」

前面三节是机制，这一节是**它们合起来为什么成立**。

### 4.1 状态不在会话里，所以进程死掉不影响它

```
dsh 管的是：会话、调度、沙箱、批准、工具注册
记忆层管的是：跨会话仍然成立的事实
```

进程退出 → 下次启动 `LifeStore` 重新读盘 → 它还是同一个它。
**dsh 会话没了，命还在。** 这也是为什么这份状态必须落成文件、而不是放在内存或某个缓存里。

### 4.2 它自己会醒，所以不需要人叫

`wake.json` 记着下一个闹钟。每轮结束向 dsh 的 `schedule` 补一个**一次性**闹钟；
到点 dsh 往原会话投一条消息并跑一个普通 turn。

三条约束写在 `lib/wake.js`（纯函数、时钟与随机数可注入，所以能确定性测试）：

- **抖动**：`every ± jitter`，不会每天同一秒醒
- **静默时段**：默认 `23:00–08:00` 不打扰
- **每日预算**：默认 6 次，按 `messageId` 幂等记账（dsh 不保证 exactly-once）
- **不整天消失**：目标被静默推到「后天」时，夹到被跳过那天的最后一个允许时刻

> 这条是 soak 抓出来的：`every=24h±4h` 时曾出现 34 小时空窗。

### 4.3 「明天还记得昨天」是数据上的事实，不是提示词里的请求

失败时它会留下一条**下一步**（`activity.next`），下一次醒来在快照里读得到。

实测（连跑七天）：

```
第 1 天 10:29  没做成 ──→ 留下了下一步
第 7 天        「接着做」还在候选里被读到
```

**这条曾经是死代码**：`choose.js` 有专门分支读它、权重给到 0.75，
但全仓库没有一处**写**它 —— 直到连跑七天日志把它暴露出来。

### 4.4 外部副作用单独管，不靠日志

发布走一个显式状态机：`draft → checked → approved → sending → confirmed / unconfirmed / failed`

- **`sending` 先落盘再发**：崩在中间，磁盘上留下的是「可能已发」，不是「从没发过」
- **`unconfirmed` 没有自动重试路径**：只有显式对账或人工确认能走出去
- **committed 永不裁剪**：丢掉一条 `unconfirmed` 等于删掉「不重发」的前提

> **诚实边界**：Telegram 没有幂等键、也没有按 id 反查的接口，所以对 Telegram 渠道，
> **并发去重只靠应用逻辑，且 `unconfirmed` 之后无法向平台确认**。
> 这不是设计取舍，是平台能力限制 —— 所以那一步必须由人来。

## 5. 不做的事（也是为什么它简单）

| 不做 | 为什么 |
| --- | --- |
| 不引数据库 | 单实例状态量小；引入 DB 会把「装一个插件」变成「部署一套服务」。原子写 + 损坏降级已覆盖可靠性 |
| 不做向量库当唯一事实源 | 检索索引可以重建，**账本不可**。重建的东西不能是权威 |
| 不把对话历史复制一份 | 那在 dsh 的 `core/session` 里；复制会带来两套不一致 |
| 不做「夜间整理并自动提升」 | 摘要与候选变更可以自动，但**不能让猜想自动变成事实** |
| 不做无限保留 | 账本有上限、outbox 有分档修剪；「追加式」不是无限保存个人数据的理由 |

## 6. 还没做 / 没验的

诚实列在这里，不藏在别处：

- **跨会话并发**：实测两个进程各自的读改写不会丢数据（`updateOutboxItem` 每次重读、且同步无 await 间隙），
  但**没有进程间锁**；真双进程压测下会看到写入被覆盖。生产路径目前只用前者。
- **长期记忆会不会「糊」**：跑三个月的记忆要不要总结、怎么总结，**未验证**。
- **`unconfirmed` 之后对人力的依赖**：Telegram 上无法自动对账，所以一条卡住的发布需要人来处理。
- **真实长跑**：七天是压缩跑的（`tools/life-week.mjs`），**没有真实等待**，也没有跨真实进程重启。
