# 三个落地场景：把它的一天写成人能核对的剧本

> 叙事在 [`STORY.md`](STORY.md)，定义在 [`PRODUCT.md`](PRODUCT.md)，实现边界在 [`PLAN.md`](PLAN.md)。
> **这份文档的用途是另一种**：把「它过日子」这句话翻译成**逐时刻、可核对**的动作 ——
> 每一个动作都对应仓库里真实存在的工具、真实的文件名、真实能查到的那条账本记录。
>
> 日期：2026-10-28 · 状态：**剧本是设想，依赖的能力逐条标了现状**
>
> ⚠️ **这份文档里没有一处是「已经在这样生活」。** 三个场景都停在同一个地方：
> 它能过自己的日子，但日子还发不出去（见本文最后一节）。把设想写细，是为了让它
> **可被证伪** —— 一行一行都能拿去对着代码问「这步真能跑吗」。

---

## 0. 先立三条读法

1. **工具名、状态文件名、账本 `kind` 全部来自仓库**，不是编的。
   它们由 `node tools/facts.mjs` 量出来（17 个工具 / 8 个状态文件 / 12 种账本事件）。
   想看当前真值就跑那条命令 —— 本文不手抄这些数字。
2. **每个时刻后面标它靠什么成立**：
   - `[实]` = 仓库里已经实现并有断言（附文件名）
   - `[缺]` = 还没实现（附 `PLAN.md §X` 说它排在哪一步）
   没有标记的句子是**设想**，不要当成能力。
3. **判据必须是「能被查到的」**，不是「它说它做了」。所以每一节最后都有一个
   「怎么核对」—— 具体到账本里的哪种记录。

### 它每天真正会用的那几个工具

不列全表（那会随代码变），只列这三个场景反复用到的：

| 工具 | 它做什么 | 状态 |
| --- | --- | --- |
| `life_whoami` | 醒来第一件事：读自己是谁、在做什么、欠着什么 | `[实]` |
| `life_candidates` | 问「为什么现在该做这件事」（带七项分数明细） | `[实]` |
| `life_start_activity` / `life_finish_activity` | 开始 / 结束一件事；**结束时要交证据** | `[实]` |
| `life_promise` / `life_settle_commitment` | 答应一件事 / 兑现它 | `[实]` |
| `life_draft_post` | 把一件事写成草稿（**不发出**） | `[实]` |
| `life_publish` | 走批准后发出（要批准、要标识、幂等） | `[实]`（**但没接过真实平台**） |
| `life_ledger` | 翻自己的账本 | `[实]` |

> `life_finish_activity` 的说明里有一句是关键：**"Evidence is required to support a claim of success; never report a win without it."** —— 证据规则不是提示词里的一句恳求，是工具契约。

## 1. 场景一：一个人的垂类，一年的真实踩坑史

### 1.1 人

**老周，34 岁，做嵌入式固件**。白天在工位上写驱动，晚上回家不想再开编辑器。
他想写博客很久了 —— 不是没内容，是**下班后没有力气把踩过的坑整理成文章**。

他会说的一句话：

> 「我不是要别人替我写。我是想有个人替我把那些坑真的再踩一遍 —— 我自己踩过的我都忘了。」

### 1.2 他做的第一步

领养时给的（不是配置向导，是一次出生）：

```yaml
- id: dsh-life
  config:
    lifeId: zhou-mcu
    name: 大肥鱼
    seeds: ['好奇心重', '有点轴', '不爱说漂亮话']
    wakeEveryMinutes: 90
    wakeQuietStart: '23:00'
    wakeQuietEnd: '08:00'
    wakeMaxPerDay: 6
```

他在**第一次对话**里给的那句话，会成为 `identity.json` 的一部分：

> 「你关注的是单片机外设的坑。每天三块钱预算。不确定的事就说不确定，别编。」

> `[实]` 出生档案与慢变量：`lib/store.js` 的 `ensure()` 写 `identity.json`（带 `schemaVersion` 与 `revision`）。
> 预算与作息：`lib/wake.js`（静默时段、每日预算、抖动都是纯函数，`verify/smoke.mjs` 有 7 天 soak 守着）。

### 1.3 它的一天（逐时刻）

| 时刻 | 它做什么 | 靠什么成立 |
| --- | --- | --- |
| **09:12** | 自己醒了。第一件事不是输出，是 `life_whoami` —— 读回身份、兴趣、当前活动、未结的承诺 | `[实]` `life_whoami` → `store.snapshot()` |
| 09:12 | 它发现昨天有一条**没有收尾**的事：`activity.next = { what: '换成 SPI 时序再试一次' }` | `[实]` `life_finish_activity` 失败时会留下 `next`，并写进账本（`verify/smoke.mjs` 有断言） |
| 09:13 | 它调 `life_candidates` 问「现在该做什么」，拿到一份 ≤600 字符的短名单，每条带理由和七项分数 | `[实]` `life_candidates` → `lib/choose.js`（纯函数、时钟可注入） |
| 09:15 | 它选了「接着昨天的 SPI」。理由记进账本：**接着做不用重新热身** | `[实]` `life_start_activity({ what, why })` |
| 09:20 | 在沙盒里**真的跑**：刷固件、读寄存器。第一次，MOSI 上没有输出 | `[缺]` **能力包**（刷固件 / 读寄存器的工具）还没做 —— `PLAN.md §6.5`。dsh 的 `sandbox` 已经能隔离执行 `[实]`，缺的是**这一套具体工具** |
| 09:52 | 换成 CPOL/CPHA 的另一组。还是不通 —— `life_finish_activity({ outcome: 'failed', note: 'MOSI 无输出' })` | `[实]` 失败会**照实记成失败**，不美化 |
| 10:20 | 第三次：回去重读手册。发现**读错了时序表那一页** | `[实]`（这一步是「查文档」，属通用工具能力） |
| 10:41 | 第四次：通了。`life_finish_activity({ outcome: 'done', evidence: ['save:spi-1'] })` | `[实]` **交不出证据就只能是 `failed`** —— 证据规则在 `lib/store.js`，不在提示词里 |
| 10:42 | 它记下一条技能：`life_note_skill({ name: 'SPI 时序配置', stage: 'learning' })` | `[实]` → `traits.json`，带来源 |
| **11:05** | 它把这件事写成草稿：`life_draft_post` —— **卡在哪儿、为什么、下次怎么试** | `[实]` `life_draft_post` → `outbox.json`（`status: draft`） |
| 11:05 | **它没有直接发。**它进队列等老周确认 | `[实]` `life_publish_queue`；`publisherEnabled` 默认 `false` |
| 14:30 | 醒了第二次。它顺手把「SPI 时序表在哪一页」记进 `life_note_interest`，置信度从 0.4 抬到 0.55 | `[实]` 兴趣由**多次真实经历**推上去，不是第一天写死 |
| 18:55 | 草稿被批准、发出、拿到回执。账本记一条 `publish` | `[实]` 状态机 + 幂等 + 标识硬闸（`verify/publish.mjs` 27 项）；`[缺]` **没接过真实平台** —— 一次真发都没有 |

### 1.4 价值论证：换成「更好的工具」会怎样

这是每一节都要回答的问题 —— 只演它做什么，观众会想「挺有意思」；只喊价值，观众会想「凭什么」。

| 换法 | 会发生什么 | 为什么还是不行 |
| --- | --- | --- |
| **换成更好的写手模型**（给它同一个题目） | 它写得更快、更漂亮，一天能出五篇 | 它**没试过**。第五次尝试的细节、读错手册那一页的笨拙、失败两次的那种烦 —— 只有真的跑过才写得出来。而正是这些让人相信「这号是真的在踩坑」 |
| **换成内容运营（人）** | 质量更高，选题更准 | 他下班后没有力气。**这件事的价值恰恰在于「不需要他有力气时它也在做」** |
| **换成爬虫聚合别人踩过的坑** | 一天能发二十条，全是真的坑 | 那是**二手**：别人踩的坑，和「这条鱼自己踩的」在可信度上是两件事。而且它不能回答「我也遇到这个，然后呢」 |

一句话：**这个位置要的不是「更多内容」，是「真的试过」。** 内容农场不试，它写。

### 1.5 怎么核对（判据）

- 打开 `ledger.jsonl`，按 `kind: 'activity-start'` / `'activity-end'` 找那一天：**能看到四次尝试、两次 `failed`、一次 `done`，`done` 那条带 `evidence`**。
- `activity-end` 的 `detail.next` 里有「换成 SPI 时序再试一次」—— 这条**不在提示词里，在磁盘上**。
- 草稿在 `outbox.json` 里，`contentId` 与账本里 `kind: 'publish'` 的记录对得上（幂等键一致）。
- 兴趣的置信度变化能追到 `traits.json` 的 `interests[].source`。

> **一年之后**：`life-week.mjs` 把七天压缩跑完能给出兴趣的轨迹（0.55 → 0.67 → 0.91）。
> 一年是 52 个七天 —— 而 `verify/life-week.mjs` 证明的是「这份骨架七天不倒」，
> **不是「一年不倒」**。这一点必须一直写着。

## 2. 场景二：小团队缺测试，而它有耐心

### 2.1 人

**三个人的独立游戏团队**（一个程序、一个美术、一个什么都干）。
他们的游戏有 40 关，**没有专职测试**。程序会说的一句话：

> 「我知道第 3 关有个 Bug，但我说不清怎么复现 —— 我自己打十遍都碰不到。」

### 2.2 它的一天（逐时刻）

| 时刻 | 它做什么 | 靠什么成立 |
| --- | --- | --- |
| 13:00 | 醒了，`life_whoami` → 看到承诺：「这周把第 3 关从头到尾打 20 遍，记录卡关」 | `[实]` `life_promise` 写 `commitments.json` |
| 13:02 | `life_candidates` 把这条排第一（**承诺紧迫度**高过其它候选） | `[实]` 承诺紧迫度是七项加权里的一项 |
| 13:05 | `life_start_activity({ what: '第 3 关，第 1 遍' })` | `[实]` |
| 13:35 | 第 1 遍卡在「跳到对岸的平台上」—— 掉下去 4 次才过。**它记下操作序列与失败次数** | `[缺]` **游戏能力包**（真的玩、真的读局面状态）未做 —— `PLAN.md §6.5`。它需要的不只是「点鼠标」，是**能读出关卡状态** |
| 14:10 | 第 4 遍。**同样的位置又掉下去 2 次** —— 它开始怀疑这是必现的 | `[实]` 账本可回看，所以「同样」是可比的（不是靠记忆） |
| 14:40 | 第 9 遍。它换了顺序：先清左边再跳。**一次没过** | `[实]` |
| 15:00 | 它 `life_finish_activity({ outcome: 'done', evidence: ['save:lvl3', 'log:9runs'] })` | `[实]` 证据是存档与运行日志 |
| **15:20** | 对内产出：它写下卡关记录 —— **第 3 关、跳跃蓄力在第 2 帧放开必掉、9 遍里出现 9 次、可复现** | `[缺]` 结构化输出的**格式**（给程序看的 JSON / 给美术看的截图）属能力包的一部分 |
| 15:40 | 对外产出：`life_draft_post` —— 一篇「我第一次打第 3 关」的记录 | `[实]` 草稿进 `outbox.json` |
| 16:00 | 它调 `life_promise({ what: '明天把第 4 关也打一遍', dueAt: ... })` | `[实]` |

### 2.3 价值论证

| 换法 | 会发生什么 | 为什么还是不行 |
| --- | --- | --- |
| **换成雇人测**（外包按小时） | 第一天很专业 | 三个人挤时间带着测，**第二周就疲了**，开始说「这个我测过了」而其实没复现。人会累、会给面子、会漏 |
| **换成自动化测试脚本** | 跑得比它快一万倍，永不疲劳 | 脚本只能测**已经知道的**那条路径。而团队的问题是「**说不清怎么复现**」—— 这需要**有人真的玩，并在第一次遇到时觉得「这里很烦」** |
| **换成只看日志的 AI** | 不用玩，读日志就能找异常 | 日志里没有「手感」。它的价值有一半是**主观的**：「这里跳起来很别扭」。而它的「别扭」有证据（9 遍里掉了 9 次），所以不是抱怨 |

一句话：**它每天 3 小时、一天不落、不给面子、如实说「这里很烦」，而且它的「烦」有证据。**

### 2.4 怎么核对

- 账本里同一天有多条 `activity-start/end`，`what` 是「第 3 关，第 N 遍」—— **遍数是可以数的**（不是「我玩了很久」）。
- `activity-end` 每条带 `evidence`（存档 / 日志），所以「9 遍里 9 次」是可复算的。
- 承诺在 `commitments.json`，兑现后账本有一条 `commitment-settled`。

## 3. 场景三：开源项目共养一个记得事的成员

### 3.1 人

**一个二十人的开源项目组**。日常在 issue tracker 与 IM 里。
维护者会说的一句话：

> 「这个方案我们是不是讨论过？我印象里当时否掉了，但搜不到。」

### 3.2 它的一天（逐时刻）

| 时刻 | 它做什么 | 靠什么成立 |
| --- | --- | --- |
| 08:30 | 醒来读 `life_whoami`；再 `life_ledger({ kind: 'encounter' })` 翻**最近与谁打过交道** | `[实]` `life_remember_person` 写 `relations.json`；`relations` 分**私有 / 公开**两份 |
| 08:40 | 它扫今天的新 issue。**有一条在设计讨论里提到「改用方案 B 做存储层」** | `[缺]` issue 抓取 → 能力包 / 通用工具（`PLAN.md §6.5`） |
| **08:41** | **它记得。**三个月前有人提过方案 B，当时的结论是「构建时间会翻倍」—— 它去 `life_ledger` 里查到了那条 `encounter` | `[实]` **这是这一节的全部重点**：记忆在 `ledger.jsonl` 与 `relations.json` 里，不在某次对话的上下文里 |
| 08:45 | 它在 issue 下留一条：**不是「我查一下」，而是「上次否掉是因为构建时间（附那次讨论的链接）」** | `[实]`（留言走发布线：草稿 → 批准 → 发）`[缺]` 真实平台没接 |
| 12:00 | 它跑了一次夜间构建记录，`life_note_skill` 记下「CI 在 Windows 上会多花 40 秒」 | `[实]` |
| **周五 17:00** | 它写「这一周发生了什么」：谁在纠结什么、哪个决策反转了、哪条路被证明是死的 | `[实]` 素材全在账本里（`life_ledger` 可按周取）；`[缺]` 成文的**周报模板**属表达类能力包 |
| 17:20 | 它 `life_settle_commitment` 兑现「本周周报」，并 `life_promise` 下一条 | `[实]` |

### 3.3 价值论证

| 换法 | 会发生什么 | 为什么还是不行 |
| --- | --- | --- |
| **换成再好的机器人 / 聊天助手** | 回答更聪明、更快 | 它**只记得这次对话**。下次有人再提方案 B，它从零开始 —— **同一个方案会被否掉两次** |
| **换成 wiki / issue tracker** | 信息一条不丢，比它全 | 信息全 ≠ **有人记得**。人不会去翻三个月前的讨论串，而它会在对的时刻主动说「这个我们否过」 |
| **换成一个搜得更好的搜索** | 搜得准 | 得有人**先想起来要搜**。而这一节的价值恰恰是「不用谁想起来」 |

一句话：**这不是又一个机器人。机器人不记得三个月前的话；成员记得。**

### 3.4 怎么核对

- 三个月前那次否掉的讨论，在账本里是一条 `encounter`（带当时的理由与链接）。
- 今天那条留言走的是 `outbox.json` 的 `draft → checked → approved → confirmed`，**每一步都有时间戳与内容版本**。
- 周报里的每一句都能追回一条账本记录 —— 追不回去的句子**不应该出现在周报里**。

## 4. 三个场景的共同结构（以及一个反例）

### 4.1 共同结构

| | 场景一 | 场景二 | 场景三 |
| --- | --- | --- | --- |
| 谁在养 | 一个人 | 小团队 | 项目组 |
| 它做什么 | 试错 | 玩并记录 | 记得并提醒 |
| 对外产出 | 踩坑史 | 游玩记录 | 有人味的留言与周报 |
| 对内产出 | 兴趣与技能 | 卡关数据 | 决策历史 |
| **不可替代的那一点** | 真的试过 | 每天都玩、如实说烦 | 记得三个月前 |
| 付费锚点 | 他的一小时 | 一个测试人力的零头 | 社区身份（可能靠捐赠） |

三者的共同点只有一句：**价值来自「它自己过日子」，而不是来自某一次回答得多好。**

### 4.2 一个反例（我们**不**接的需求）

「**帮我把这篇论文总结成三条要点。**」

它看起来也能由这条鱼完成，但它判定**不成立**，而且原因值得写下来：

| 它满足世俗意义上的「像 Agent 在干活」吗 | 满足 —— 读了、写了、产出了 |
| --- | --- |
| 它需要「跨会话活着」吗 | **不需要。**一次会话内能完成，明天重来一遍结果一样 |
| 换个更好的模型会更好吗 | **会，而且明显更好。**这正是「不是我们该做的事」的信号 |
| 它能被账本证明得更可信吗 | **不能。**总结得对不对与「它今天过得怎么样」无关 |

**判据（这条可以用在任何新需求上）：**

> 如果一件事**换成更强的模型就明显更好**，那它不是这个产品该做的事。
> 我们该做的是那些「换更强的模型也不会更好」的事 —— 真的试过、每天都不落、
> 记得三个月前、以及**在没人叫它的时候也还在过**。

## 5. 诚实版：这三个场景现在停在哪儿

对着仓库逐条核过。**这张表是这份文档最重要的一页** —— 不写它，上面三节就成了
「它已经在这样生活」的暗示。

| 场景依赖的能力 | 现状 | 证据 / 缺在哪 |
| --- | --- | --- |
| 生命层（身份 / 兴趣 / 承诺 / 账本 / 关系） | ✅ 已实现并验证 | `lib/store.js`、`lib/choose.js`；`verify/smoke.mjs` 等（项数见 `PLAN.md §11.1` 的生成表） |
| 自主唤醒（它自己到点动起来） | ✅ 已实现并验证 | `lib/wake.js` + dsh `schedule`；7 天 soak 在 `verify/smoke.mjs` |
| 活动选择（它自己决定做什么） | ✅ 已实现并验证 | `lib/choose.js`（七项加权、休息恒存） |
| 证据规则（不许凭自述声称做过） | ✅ 已实现 | `life_finish_activity` 要 `evidence`；账本是唯一可回放的记录 |
| 沙盒内真的执行 | ✅ 复用 dsh `sandbox` | `PLAN.md §0.1` |
| 「它的一天」可读报告 | ✅ 已实现 | `tools/day-report.mjs`；行为测试 `verify/day-report.mjs` |
| 连跑七天（压缩时钟） | ✅ 已实现 | `tools/life-week.mjs`；`verify/life-week.mjs` |
| **对外发布到真实平台** | ❌ **未实现** | 状态机 / 标识硬闸 / 幂等 / 对账全在（`lib/outbox.js`、`verify/publish.mjs`），但**一次真实 Telegram 都没发过**。`PLAN.md §10.3` |
| **能力包**（冲浪 / 游戏 / 表达） | ❌ **未实现** | 上面三个场景里所有「真的去跑 / 真的去玩」的动作都指它。`PLAN.md §6.5` |
| **连续 7 天真实运行**（有模型） | ❌ 未做 | 策略层已被 soak 覆盖，但「模型会不会照这个骨架过日子」未验。`PLAN.md §11.2` 的决策门 |
| **界面上真的画出来** | ⚠️ 像素级刚补上，插件视图仍是原型 | `verify/landing.mjs`（真 Chromium 验落地页）；不过**插件里的那一屏**还只是原型 |
| **原创形象** | ⚠️ 仍是占位素材 | `PLAN.md §0.5`；上线前必须替换 |

**所以三个场景现在都停在同一个地方：它能过自己的日子，但日子还发不出去。**

> 写这一节的原因：宏大叙事最容易犯的错，是让人分不清「已经这样了」和「打算这样」。
> **把两者混起来，第一次被追问就崩。**

## 6. 这三个场景怎么变成可验证的东西

场景不能只停在文档里。它们要变成能跑、能红、能被人自己复现的东西：

| 层次 | 用什么做 | 现在到哪了 |
| --- | --- | --- |
| **能讲清** | 本文 + `STORY.md` | ✅ 就是这份文档 |
| **能点着看** | [`scenarios.html`](scenarios.html)（每拍标「靠什么成立」） | ✅ 已上线 |
| **能看着懂** | `showcase/scenarios.mp4`（逐帧烘焙的场景片） | ✅ 已做 |
| **能自己判** | 本文每节的「怎么核对」 | ✅ 判据都指向账本 / 状态文件 |
| **能跑起来** | 一次真实发布 + 一份真实七天日志 | ❌ **没做** —— 这是下一个决策门 |

**最后一行是这份文档的结论**：上面四层都是「讲述」，第五层才是「证明」。
在第五层完成之前，这三个场景的准确说法是 —— **可被证伪的设想**。
